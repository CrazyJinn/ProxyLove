# Schema 单源化方案（C'：软单源——skill 直读 Schema）· 待拍板

> **病根**（2026-11-13 模拟写入流程实证）：写入 skill 不读 Schema，靠 SKILL.md 内嵌的①字段表 ②cypher SET 模板两份手工副本工作。模板 SET 什么，LLM 就认为字段全集是什么——每 skill 一份各自漂移的「事实 Schema」。char-concept-designer 的 appearance 三处残留（有生成无 SET 静默丢失）即此病。vibe 家族改名若晚一天，就是「漏写新字段」的镜像事故。
>
> **方案 C' 目标**：删除 skill 内嵌副本，写入 skill 在流程内**直接 Read Schema 对应节点节**，由 LLM 按真源现场生成字段清单与 SET 语句。不建 yaml、不做强校验——单源靠「读得到」保证，不靠「校验得住」保证。风险接受：LLM 偶发漏读/读错由审计侧（体检页 + 定期全图扫描）兜底。

---

## 一、总体架构

```
00_init/Schema/*.md          ← 唯一单源（人读即机器读——LLM 直接 Read）
        │
        ▼
各写入 skill SKILL.md
  段1 查状态（不变）
  段2 生成前：Read Schema 对应节点节（字段表即字段全集）
       ——SKILL.md 内嵌字段表【删除】
  段3 保存结果：LLM 按 Schema 字段表现场写 SET 语句
       ——内嵌 cypher 模板降级为「形态示例」（只示范 MERGE 锚定/边方向/sync 约定，
         不列字段清单）；已废字段以 Schema 内「已废注记」为准，读到即避开
        │
        ▼
审计侧兜底（已有设施，不加码）
  dashboard 体检页 + 定期全图扫描（schema_audit 式白名单对账）
  ——LLM 偶发漏读/读错在这里暴露，事后修
```

## 二、skill 侧改造模式（每个写入 skill 一次）

```markdown
### 段2 完成任务（生成前）
Read 00_init/Schema/角色美术.md 的「立绘（StandingIllustration）」节——
字段全集、必填、类型、已废注记以该节字段表为准，**不凭记忆写字段**。

### 段3 保存结果
按上一步读到的字段表写 SET 语句（形态：MERGE 锚 id → SET 白名单字段 → status）。
写后读回验证（既有纪律不变）。
```

SKILL.md 保留的东西：
- **形态示例 cypher**：MERGE 锚定写法、边方向、sync 约定、status 终值——这些是流程语义，Schema 不承载
- **性质判定纪律**：禁情绪类 eye 描述、tts_text 禁改汉字这类——skill 本职
- **删除的东西**：内嵌字段表（全字段+示例值）、SET 字段清单逐行模板

## 三、Schema .md 侧的配套改造（让 LLM 读得准）

C' 成立的前提是 Schema 节点节本身**可直读、无歧义**，需小幅整理：

1. **每个节点节头部加一行直读锚**：`> 字段全集以本表为准；skill 写入前 Read 本节，不凭记忆写字段。`
2. **字段表格式冻结**：表列固定（字段/中文/类型/必填/说明），说明列不藏结构性信息（枚举值一律列在表下专段）——保证 LLM 解析稳定
3. **废弃字段不留表**（2026-11-13 拍板）：字段废弃时用户自行同步清理 Schema 注记与图内数据，不建废弃字段表——表中没有的字段即非法字段，LLM 读不到自然不写；「旧字段复活」风险由审计侧兜底（见 §五）

## 四、变更流程（改造后的 Schema 演进路径）

```
旧：改 .md 字段表 → 逐 skill 找内嵌副本手工同步（漏一处 = 事故）
新：改 .md 字段表（废弃字段连注记一并删净，图内数据同批清理）→ 全部 skill 下次运行自动读到新表
    （零 skill 改动）
```

## 五、审计侧兜底（不加新设施，明确既有职责）

| 层 | 设施 | 拦什么 |
|---|---|---|
| 写入时 | Schema 直读（本方案） | 模板滞后型脏写（主体，防新增） |
| 事后 | dashboard 体检页 + 定期 schema_audit 式全图扫描（白名单脚本已验证可行，11-13 跑过全库零违规） | LLM 漏读/幻觉字段、读错类型（兜底，查存量） |
| 事后 | 责任矩阵（生产方×消费方登记） | 写入方漂移（谁在写不该写的字段） |

## 六、与强校验版（原 C/yaml）的取舍对照

| 维度 | C'（本方案：LLM 直读） | 原 C（yaml 强校验） |
|---|---|---|
| 单源保证 | 靠「读得到」——skill 每次运行读真源 | 靠「校验得住」——写入瞬间机器比对 |
| 拦截时机 | 事前（LLM 读到的表即全集）+ 事后（审计） | 事前 + 写入瞬间硬拦 |
| 失效模式 | LLM 漏读/幻觉 → 脏写入库，审计事后发现 | 几乎无（除绕过 cypher_exec 的路径） |
| 建设成本 | 低：17 skill 删内嵌 + Schema 小整理，无新代码 | 高：yaml ~800 行 + tool ~200 行 + cypher_exec 改造 + node_fields 生成链 |
| 心智负担 | 无新概念，与现有「skill 三段式」同构 | 多一层 yaml↔.md 对账纪律 |
| 漂移面 | Schema .md 单一（副本全删） | .md + yaml 双源（diff-md 守门） |

选 C' 的隐含承诺：接受偶发脏写、靠审计兜底——与项目一贯的「信号标红而非门禁拦截」治理偏好一致。
