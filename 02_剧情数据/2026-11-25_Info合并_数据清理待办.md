## 2. 过审方式

三张表都带推荐。回改动（整表照推荐也行）→ 复述终表 → 确认 → 才生成迁移文件（单事务，语句全文先过目）。

**已裁（2026-11-26）：测试期草稿的引用指纹不用清理。** stale 的以后自行过期，稳定后用户全量重跑指纹。后续批次不做 stale 影响分析，也不重算指纹头。

**会波及存量草稿的操作**（仅供了解）：删除、改标题、合并，都会让「引用」列里那些草稿在下次进 chapter-dialoguer 时报 stale。7 份待重跑的跑团草稿本来就会重产；存量 小说.md 被重新推进时会 stale，按既有链路转 tabletop 重跑。想保新鲜的话，可以按 id 把指纹头的 hash 重算（默认不做）。

**合并时保留被草稿引用的那个 id**，另一条删除、其认知改挂过去。

## C. 操作形态（生成迁移文件时照抄）

| 操作 | 语句形态 |
|---|---|
| 删除 | `MATCH (n {id:'…'}) DETACH DELETE n` |
| 改标签 | 已执行（§F）；回滚语句见 §F |
| 改标题 | `MATCH (i:Info {id:'…'}) SET i.title='维度：值'` |
| 拆分 | 新建 `Info` 节点；挂靠边两端先 `MATCH` 绑定，再 `MERGE (h)-[r:has_info]->(i) ON CREATE SET r.sync=false` |
| 事件 Info 转固有 | 删 `establishes` 边；挂靠边两端先 `MATCH` 绑定，再 `MERGE (h)-[r:has_info]->(i) ON CREATE SET r.sync=false` |
| 认知改前史 | `MATCH (:Event)-[f:forms]->(c:Cognition {id:'…'}) DELETE f` |
| 合并时的认知改挂 | 删旧 `about`；两端先 `MATCH` 绑定，再 `MERGE (c)-[r:about]->(i) ON CREATE SET r.sync=false` |
| 新增前史认知 | `MERGE (c:Cognition {id:'<snowflake>'})` + `has_cognition` + `about`，不建 forms |
| 新增故事内认知 | 同上，再加 `forms` 锚事件 |

- **建边一律两端先 `MATCH` 绑定**，再 `MERGE (a)-[r:类型]->(b) ON CREATE SET r.sync=false`：带关系模式的 `MERGE` 会把整段模式新建出来、复制出空壳端点（批次 2 实测，见 §F）。执行文件里不要放 `--` 注释行，每条语句以 `;` 结尾。
- 迁移前先备份：导出受影响的全部节点属性与边、各类计数。回滚 = 按备份反向执行。
- 单事务：`cypher_exec.py -f <文件> --multi`，写后读回验证。
- 所有涉及的边 `sync=false`，不触发级联；Info / Cognition 无 status。
- 迁移前确认守护进程未运行、`.tmp/tabletop/` 下没有运行中的节。
- 读回口径：旧标签 = 0；混轴 = 0；孤儿 = 0；无 forms 且指向事件 Info 的认知 = 0；前史认知条数、Info / Cognition 总数与终表一致。
